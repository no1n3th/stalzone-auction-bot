# Решения (ADRs) — обновлено к ЗБТ

## D1. Outbox — единственный источник правды доставки (P0-2.9)
При сбое доставки Discord-сообщение остаётся в outbox и повторяется sweep-воркером;
DLQ получает только «ядовитые» сообщения (битый JSON) и исчерпавшие попытки
(`attempts >= MAX_OUTBOX_ATTEMPTS`). Два механизма надёжности на одно сообщение
устранены — дубль-доставки невозможна по построению: строка закрывается (`sent_at`)
только после фактической отправки, повторный sweep не находит закрытых строк,
а свежие строки (< 120 с) фильтром `MIN_OUTBOX_AGE_SEC` не отдаются, пока могут
лежать в памятной очереди.

## D2. Время продажи (P0-4)
Все рыночные окна считаются по `coalesce(sold_at, created_at)`. Для legacy-строк
реальное время продажи невосстановимо — миграция `006_history_effective` ставит
суррогат `sold_at = created_at` (время скачивания). Это осознанное приближение;
новые строки получают настоящий `sold_at` из поля `time` API (ISO-8601 или epoch).

## D3. Дедуп-сигнатура лота включает цену (P1-3)
Снижение цены того же лота даёт новый алерт — осознанное решение (торговец
переставил лот дешевле). Ограничение: без `lot_id` в ответе `/lots` разные лоты
с одинаковой ценой сливаются в одну сигнатуру (фикстура `tests/fixtures/lots.json`
подтверждает отсутствие поля `id`).

## D4. Маркер цены не рисуется в PNG-графике (P1-5)
Day-ключ кэша общий для всех лотов группы; цена лота уже присутствует в embed.
Маркер исключён вместо усложнения ключа — дешевле и устраняет класс бага целиком.

## D5. Ат-least-once алерты (P1-3)
`mark_sent` выполняется ПОСЛЕ publish/enqueue: краш между отправкой и пометкой
даёт дубль-алерт, а не потерю. Потеря недопустима, дубль терпим (редок и виден).

## D6. Безопасность (P2)
- PBKDF2-SHA256: 120 000 → 600 000 итераций; перехеширование — прозрачно при входе.
- `/metrics` открыт по умолчанию (совместимость), закрывается `METRICS_TOKEN` (?token=).
- Заголовки безопасности (CSP/nosniff/DENY/Referrer-Policy) на всех ответах.
- Регистрация: порядок «режим → занятость логина» (нет перебора логинов), lock до commit.

## D7. Outbox-backoff и per-webhook доставка (3.1.1)
Код приведён в соответствие с D1: `OutboxRepository.pending()` фильтрует
`next_attempt_at` (sweep больше не реэнкьюит строку каждый цикл поверх бэкоффа
в 5 минут), а `_send_batch` не кладёт в DLQ payload с `_outbox_id`. Мультивебхук:
частичный успех ретраит только упавшие хуки (`_send_one`), доставленные
сообщения не дублируются.

## D8. Публичные эндпоинты (3.1.1)
`/api/market|daily-prices|forecast` без авторизации защищены `PublicEndpointGuard`:
скользящий лимит 30 запросов/мин/IP + кэш ответов 45 с (in-memory, одного
инстанса достаточно — бот работает в одном контейнере).

## D9. Удаление пользователя (3.1.1)
Нельзя удалить себя и последнего админа (409). Сделки удаляемого аккаунта
удаляются вместе с ним, чтобы не достались новому аккаунту с тем же логином;
все сессии отзываются (`session_store.drop_user`).

## D10. Feature flags админки реально управляют рантаймом (P1-10, 3.1.1)
`config_reload_worker` раз в 30 с читает `feature_flags` в `container.runtime_flags`
и применяет side-effects: `charts_enabled` -> `ChartService.enabled`,
`discord_enabled` -> `notifier.paused` (enqueue молча дропает). Воркеры читают
флаги из памяти через `workers.flag_on`: `scanner_enabled`,
`history_sync_enabled`, `meta_monitor_enabled`, `season_monitor_enabled`.
Отключённый воркер продолжает бить heartbeat — `/health/ready` зелёный
(осознанное отключение, не сбой). Отсутствующий в таблице флаг = дефолт True —
UI не может сломать бот удалением строк. ConfigRepository-пороги сознательно
не «горячие»: менять экономику на лету опаснее, чем паузить подсистемы.
## D11. Иконки предметов — путь из листинга, не угадайка (P0-1, 3.1.1)
В `stalcraft-database` иконки лежат в `ru/icons/<подтип>/` (например
`ru/icons/artefact/...`). `sync_items_db` сохраняет поле `icon` записи в кэш;
Discord-embed строит URL как
`raw.githubusercontent.com/EXBO-Studio/stalcraft-database/main/ru/<icon>`.
Нет иконки — embed без thumbnail (пустой/ошибочный URL убивал webhook 400, P0-5).
## D12. Стабилизация по пост-инвалидационным продажам (P1-7, 3.1.1)
`window_spread_pct(..., since=)` считает спред только по продажам после
инвалидации (шкала из штампа `invalid:*`). Продажи до дампа больше не
удерживают флаг бесконечно; TTL-фолбэк (2× окно) сохранён для неликвида.
